# Spotify Connect feasibility

Decision on 2026-11-16: defer implementation in 1.4. This is a documentation review, not a tested integration. No Spotify account, token, device or catalog playback was used. No supported podcast example has been established.

The [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk) creates a browser Connect device for Spotify content. It does not make an arbitrary `AudioSource.src` playable through Connect. Controlling an existing Connect device instead uses Spotify's Web API; creating a browser device is unnecessary for that route.

A concrete candidate for a separate feasibility experiment is the catalog track `spotify:track:4iV5W9uYEdYUVa79Axb7Rh`, used in Spotify's [Start/Resume Playback example](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback). This is an API documentation example, not a verified currently playable item or a mapping from our audio fixtures. Validate availability for the authorized user's market/account before use. An episode must have a separately established Spotify catalog identity; the documented track example does not establish podcast support or timeline equivalence with an RSS audio file.

[Playback transfer](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback) requires Premium and warns that ordering across Player API calls is not guaranteed. The operation controls a selected Spotify device, not a receiver accepting our media URL. A future experiment must bind identity, commands, observed position, user intent and source revision to the selected Spotify item before routing shared cues. Do not reuse RSS chapter timestamps across different edits or ad insertions without verified timeline mapping.

The [SDK getting-started guide](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started) requires a Premium user's token and lists restrictions on synchronizing sound recordings with visual media. The SDK overview also requires prior written approval for commercial projects. These documented constraints prevent us from treating the library's timed chapter-card demo as a permitted Spotify integration. No exception or approval is assumed.

For a browser-only experiment, use application-owned [Authorization Code with PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow), explicit device selection, and only the scopes needed for the chosen route. Existing-device playback control needs `user-modify-playback-state`; discovery/observed playback needs the applicable read scope. The SDK adds its streaming requirements only if creating a browser device. Token acquisition and renewal belong to the consuming integration, outside generic `AudioSource` and persisted state. No client secret belongs in the browser. A new backend is not inherently needed for PKCE; a consumer choosing server sessions must own OAuth/session binding, renewal and revocation.

Current [development-mode rules](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide) require an active Premium app owner and limit new apps to five users and one client ID per developer, with documented grandfathering. [Extended quota](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) has a separate organizational application process. A general-purpose library cannot promise that every consumer can deploy an integration at scale.

Revisit only with a concrete content/account example, permitted usage for its UI, explicit authentication/renewal ownership, and real-device tests. Then assess a separately enabled optional adapter. No Spotify SDK, credentials, provider identifiers or server dependency is added to the browser core in this prototype. This decision completes the feasibility note, not Spotify Connect support.
